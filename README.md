# pEditor

スマホでコードを書くためのエディタ。ブラウザで動く PWA で、**エディタエンジンは自作**（CodeMirror / Monaco などは使っていません）。ランタイム依存ゼロ、ビルド後 66 kB（gzip 21 kB）。

## 使ってみる

```bash
npm install
npm run dev        # スマホから開けるよう LAN に公開されます
```

表示された `http://<PC の IP>:5173/` を同じ Wi-Fi のスマホで開き、ブラウザの「ホーム画面に追加」でインストールすると全画面のアプリになります。

```bash
npm run build      # 型チェック + 本番ビルド → dist/
npm run preview    # dist/ を配信
npm run check      # 型チェック + ユニットテスト
npm test           # ユニットテスト（Node の組み込みテストランナー）
npm run icons      # public/icons/*.png を再生成
```

`dist/` は静的ファイルだけなので、任意の静的ホスティングにそのまま置けます。

## デプロイ

`.github/workflows/pages.yml` が push のたびに型チェック・テスト・ビルドを走らせ、GitHub Pages に公開します。

**初回だけ手動設定が必要です** — リポジトリの **Settings → Pages → Build and deployment → Source** を **GitHub Actions** に変更してください。ワークフローのトークンには Pages サイトを新規作成する権限がない（`GITHUB_TOKEN` にリポジトリ管理権限が付与されないため）ので、ここだけは自動化できません。設定後、Actions タブから最新のワークフローを Re-run すれば公開されます。

公開先:

| URL | 内容 |
| --- | --- |
| `/` | PWA 本体。ホーム画面に追加でき、オフラインでも動きます |
| `/peditor.html` | 全部入りの HTML 1 枚（`npm run build:single`）。保存してそのまま開けます |

## スマホで書くために解いた問題

エディタの難しさはテキスト編集そのものより、**スマホ特有の制約**にあります。実装の重心もそこに置いています。

| 問題 | 対処 |
| --- | --- |
| ソフトキーボードが画面下半分を覆う | `visualViewport` に追従してアプリ全体をリサイズ（`src/ui/viewport.ts`）。`100vh` は使わない |
| スマホのキーボードでコードは書けない | コード用のキーボードを自作（`src/ui/keyboard/`）。数字は常時表示、記号レイヤーは括弧が最上段、`->` `=>` `::` `!=` `==` は1キー。上端のバーをドラッグで高さを変更でき、設定は記憶される |
| スクロールがカクつく | 非 passive な `touchmove` を排除し、スクロール中の強制同期レイアウトとスタイル再計算を除去。オーバースキャンを広げ、その帯の中を動く間は DOM に一切触れない |
| でも日本語は IME でしか打てない | `⌨` キーで OS のキーボードと相互に切替。切替中もキャレットは保持される |
| IME（日本語入力）が必要 | 非表示 `<textarea>` に focus を保持し、composition イベントを編集コマンドに変換。変換中の文字列はバッファに直接書き込むので、折り返し・スクロール・キャレット位置が変換中も正しく動く |
| IME 候補ウィンドウが変な位置に出る | textarea をキャレット位置に追従させる。ただし `pointer-events: none`（付けないとタップを奪ってダブルタップが壊れる） |
| ピンチするとページ全体が拡大する | ピンチを横取りして、**エディタの中身だけ**を拡大縮小（`src/editor/input/pinch.ts`）。指を動かしている間は CSS `transform: scale()` で連続追従し、離した瞬間に実際の文字サイズへ畳み込む。文字セルが変わるので行番号・行間・折り返し幅も同じ数値から追従する |
| 指がキャレットを隠す | 行の下に掴めるハンドルを表示。ドラッグ中は端で自動スクロール（`src/editor/input/handles.ts`） |
| 横スクロールが苦痛 | 折り返しを既定 ON。インデントを保って折り返す |
| タップ後にキーボードが閉じる | touch 後に発火する互換 `mousedown` の既定動作を抑止（これが focus を奪っていた） |
| 日本語コメントでキャレットがずれる | East Asian Width を考慮した桁計算。全角文字の描画幅を明示指定して、フォント任せにしない |

### 全部が「文字セル」の算術に乗っている

ビューの土台は 1 つの前提です — **すべての文字は `charWidth` の整数倍の幅で、すべての行は `lineHeight` の高さ**。

これが成り立つ限り、座標 ⇄ 位置の変換は掛け算と割り算だけで済みます。`getBoundingClientRect()` も `Range` 測定もゼロ。指でキャレットをドラッグしている間、1 フレームごとにヒットテストしても重くなりません。

前提はレンダラ側が守ります（`src/editor/view/renderer.ts`）:

- タブは幅を明示した `padding-left` で描く
- 全角文字の連続は `width` を明示した `inline-block` に入れる（フォントの CJK 送り幅が 2 倍ちょうどでなくても、行内でズレが累積しない）

折り返しも同じ算術の上に載るので、DOM 測定なしで折り返し位置が決まります。

### 差分だけを作り直す

- **バッファ**は行の配列。編集は `splice` 一発
- **レイアウト**は行ごとにキャッシュし、編集時は `splice` でずらす。編集していない行の折り返し結果はそのまま生き残る
- **ハイライト**は行単位 + 行間の持ち越し状態。`states[i]` は「i 行目を処理する前の状態」なので、描く行の分だけ計算すれば足りる
- **DOM** は表示範囲だけ（前後 6 行のオーバースキャン付き）。2 万行のファイルでも DOM 上の行要素は 40〜47 個

20,000 行 / 3.4 MB のファイルで、1 打鍵あたりのコストは 200 行のファイルと変わりません（実測: どちらも計測下限の 33 ms＝rAF 2 フレーム）。

### ピンチは transform で、確定はレイアウトで

ブラウザ標準のピンチズームが指に貼り付くのは、コンポジタが**連続的な `scale`** を当てているからです。同じ仕組みをエディタの中身にだけ使います。

- **指が触れている間**: `transform: scale()` を当てるだけ。transform はコンポジタのプロパティなので、レイアウトもスタイル計算も再描画も起きず、指の動きにそのまま追従します
- **行番号と本文は別々にスケールし、どちらも左端を基準にします**。まとめてピンチ中心を基準に拡大すると、ガターの左端が画面外へ押し出され、行番号だけが横に流れて消えます。左端に固定すればその場で拡大され、縦の基準を共有しているので行番号と本文行はずれません。本文はガターの伸びた分だけ右へずらし、重ならないようにします
- **指を離した瞬間**: スケールを実際の `fontSize` に畳み込み、そこで初めて本物のレイアウトをやり直します。拡大でぼやけた文字がこの瞬間にシャープに戻ります（地図や PDF ビューアと同じ割り切り）

最初の実装は移動のたびに `fontSize` を計算し直していました。フォントサイズは整数ピクセルなので**飛び飛びの値にしかならず**、しかも各段階で全文書を折り返し直します。これは速度の問題ではなく仕組みの選択の誤りで、いくら最適化しても連続的にはなりません。

2000行の文書に対しピンチ操作24回:

| | ピンチ中のレイアウト | 離したとき |
| --- | --- | --- |
| 文字サイズを都度変更 | 48 回 | 0 |
| transform + 確定時に畳み込み | **1 回** | 4 回 |

ページ全体を拡大するブラウザ標準のズームを使わないのは、ツールバー・ステータスバー・キーボードまで一緒に拡大され、画面が狭くなって横スクロールも発生するためです。拡大したいのはコードだけです。

### スクロール中は DOM に触らない

スクロールはコンポジタの仕事で、JavaScript が割り込むほど遅くなります。そこで:

- **タッチリスナーは可能な限り passive にし、非 passive なものは即座に抜ける**。非 passive なリスナーは `preventDefault()` を呼びうるため、ブラウザはハンドラの完了を待ってからでないとスクロールを開始できません。ただし**ピンチには非 passive が不可欠**です:

  - `touchstart` / `touchmove` は非 passive。ただし1本指のときは指の本数を見て即 `return` し、**cancel しません**（＝ブラウザは通常どおりスクロールします）
  - 2本指の `touchstart` で `preventDefault()` し、ジェスチャを自分のものとして宣言します。**これを怠るとブラウザはピンチを2本指パンとして扱い、最初の1回以降 `touchmove` をページに配信しなくなります** — 画面上は「1度カクっと拡大して、あとは動かない」に見えます
  - リスナーを `touchstart` の中から遅延登録するのも同じ理由で不可です。**すでに始まったジェスチャは、後から追加したリスナーでは cancel できません**
  - pointer 系はどれも cancel しないので passive です
- **可視範囲より広い帯を描いておき**、その中を動いている間はレンダリング自体を呼びません。スクロールイベントで走るのは「帯を出たか」の判定だけです
- **同じ値の style は書きません**。CSS カスタムプロパティは継承するので、1回書くだけでサブツリー全体のスタイルが無効化されます
- キャレットの点滅リセットは `offsetWidth` を読んで強制レイアウトを起こすので、**キャレットが実際に動いた時だけ**実行します
- **行の高さは整数ピクセルに丸めます**。1.5 倍の行間だと行が 67.5px のような半ピクセル位置に乗り、テキストはスクロールのたびに再ラスタライズされます（コンポジタが平行移動するだけでは済まなくなる）。一方、**文字幅は丸めません** — フォントの実際の送り幅であり、丸めると桁計算と描画が1文字ごとにずれていくためです
- スクロールハンドラからレイアウト読み取り（`clientHeight`）を排除し、非表示のハンドルや IME 位置の同期も走らせません
- **`visualViewport` の変化で無駄な再レイアウトを起こさない**。Android のブラウザタブでは、スクロールに伴ってアドレスバーが伸縮し `visualViewport` が連続的に変化します。その値を毎回 DOM に書き戻すと、アプリのグリッドがリサイズされ → エディタの `ResizeObserver` が発火し → 文字セルの再測定（`getBoundingClientRect`）で**スクロールのフレームごとに強制同期レイアウト**が走ります。値が変わっていなければ書かず、変わったのが高さだけなら再測定もしません（文字セルも折り返し幅も高さには依存しないため）。カスタムプロパティも `documentElement` ではなくアプリ要素に置きます — 継承するので、ルートに書くとページ全体のスタイルが無効化されます

  高さのみの変化20回に対する強制再測定の回数: **19 → 0**（幅が変わったときの再計算はそのまま）

3,000 行を指で連続スクロールしたときの実測（Chrome DevTools Protocol の `Performance.getMetrics`）:

| | レイアウト回数 | スタイル再計算 | レイアウト | スタイル | JS |
| --- | --- | --- | --- | --- | --- |
| 対策前 | 143 | 377 | 28 ms | 23 ms | 58 ms |
| 第1段階 | 7 | 7 | 7 ms | 4 ms | 30 ms |
| 現在 | **5** | **5** | 6 ms | 3 ms | **20 ms** |

なお `Performance.getMetrics` はペイントと合成を含みません。整数行高やノード数削減（行あたりの span を 23% 削減）は実機の描画に効く対策で、ここには現れません。

### Undo

スナップショットではなく逆編集を積みます。連続入力は 600 ms 以内かつ隣接していれば 1 ステップにまとめ、改行は前後どちらとも結合しません。IME の変換は「変換前 → 確定後」の 1 ステップとして記録されるので、Undo 一回で変換がまるごと戻ります。

## テスト

DOM に依存しないコア（バッファ・桁計算・折り返し・Undo・トークナイザ）は Node の組み込みテストランナーで直接実行します。相対 import に `.ts` 拡張子を付けてあるので、トランスパイル不要でソースをそのまま読めます。

```bash
npm test      # 102 tests
```

ブラウザ側の挙動（IME・タップ・キーバー・折り返し）は Playwright で確認しています。

## 現状の範囲

**入っているもの** — 閲覧 / 編集モードの切替（既定は閲覧）・GitHub public repository の検索・URL を貼っても開ける・最近開いたリポジトリ・「リポジトリを開く」と「ファイルを見る」を分けた 2 画面のファイルパネル・Markdown ビュアー・コード構造に沿った折り返し（Smart wrap）・操作は全て画面下部のバー・開いたファイルの IndexedDB 保存と復元・変更マーク・編集・選択・Undo/Redo・折り返し・シンタックスハイライト（TS/JS・Rust・C・JSON・CSS・HTML・Markdown）・自動インデント・括弧の自動補完・コメントトグル・行移動/複製・タッチ操作一式・ピンチで文字サイズ変更・コード用キーボード（OS キーボードと切替可）・設定・テーマ・オフライン動作・ファイルを開く / ダウンロード。

**入っていないもの** — GitHub への commit、認証（private repository、検索枠の拡大）、diff 表示、リポジトリ内のファイル全文検索、タブ、複数カーソル、コード実行・プレビュー、補完。

既知の制約:

- GitHub API は未認証で 1 時間 60 リクエストです。ディレクトリを開くたびに 1
  回使いますが、**ファイル本文の取得はこの枠を使いません**（raw から取るため）。
  一度開いたディレクトリとファイルは IndexedDB に残るので再取得もしません
- リポジトリ検索は別枠で、未認証だと 1 分 10 回です。キー入力ごとには投げず、
  450ms 打鍵が止まってから 1 回だけ投げ、次の入力が来たら前の要求は中断します。
  URL を貼った場合は検索せず、そのまま開ける行を出します
- Workspace の基準 commit は開いた時点で固定します。ブランチが進んでも自動では
  追随しません（編集内容の基準が動かないようにするため）
- ブラウザのデータを消すと編集内容は失われます
- ハイライトは正規表現ベースのトークナイザで、構文解析はしていません
- 描画済み行のレイアウトはキャッシュしたまま破棄しないので、巨大ファイルを端から端までスクロールするとメモリが漸増します（2 万行で約 30 MB）
